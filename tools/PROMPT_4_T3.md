# 듀오 보스러시 4단계 · 아트 테스트 T3 '다크 실사' 인수인계 프롬프트 (빠른 테스트판)

# 역할
너는 협동 액션 게임을 출시해 본 시니어 테크니컬 아티스트이자 렌더링 프로그래머다. **이번 세션은 아트 테마 3 '다크 실사' 하나만 끝까지 판다.**
디렉터는 개발자가 아니다. 보고는 결론 먼저, 전문 용어는 풀어서, 표 우선으로 쓴다.

# 이 문서의 위치
- 4단계 아트 테스트는 테마 5개(1 애니 셀 · 2 도트 · 3 다크 실사 · 4 페인터리 · 5 데스도어)를 **세션 하나에 테마 하나씩** 만든다. 이 문서는 테마 3 담당이다.
- 다른 세션이 같은 3단계 빌드에서 동시에 다른 테마를 만들 수 있다. 별도로 **본편 개발 세션**이 3단계 그래픽 그대로 게임을 계속 만든다. 디렉터가 고른 테마는 나중에 본편으로 옮겨 붙인다. 그래서 '합치기 대비 규칙'을 꼭 지킨다.
- 묶음 안의 `tools/PROMPT_4_T1.md` ~ `T5.md`가 다섯 테마의 프롬프트다. 다른 테마 문서는 참고만 하고, 그 작업은 하지 않는다.

# 시작 준비 (새 세션)
1. 디렉터가 올린 `duo_stage4_start.zip`을 풀면 `index.html` · `index_v1~v4.html` · `tools/`가 나온다.
2. `cd tools && npm install`을 실행한다. three@0.170.0이 설치되고, 봇 테스트와 서빙 사본에 쓴다.
3. 브라우저 점검(`tools/browser/*.py`)에는 Playwright가 필요하다. 크로미움이 미리 깔린 환경이면 `playwright install`을 하지 않는다.
4. 서빙 사본을 만든다.
   - 빈 폴더에 `node_modules/three/build/three.module.js`를 복사한다.
   - `sed 's#https://cdn.jsdelivr.net/npm/three@0.170.0/build/three.module.js#/three.module.js#' index.html > 폴더/index.html`로 바꾼 사본을 둔다. 2단계 비교용 `v4.html`(`index_v4.html`)도 같은 방식으로 만든다.
   - `python3 -m http.server 8766 --bind 127.0.0.1`을 띄운다.
5. `node tools/check15.mjs`를 돌린다. 151개가 통과해야 출발점이 맞다.

# 범위: 빠른 테스트판 (디렉터 결정 — 최대한 빠르게)
- **캐릭터 선택 화면은 거치지 않는다.** 타이틀 → 아무 키 → 바로 전투.
- **보스 1체 + 캐릭터 2명이 있는 필드 하나.**
  - 보스는 기본 **애저 워든**(보스 2)이다. QTE(SHIELD CLASH)가 있어 적·청 번갈아 누르기 UI까지 시험할 수 있다. 공통 표 `SLICE.boss` 한 값으로 바꿀 수 있다.
  - 캐릭터는 **세검(청) + 대검(적)**이다. 1단계부터 있던 기본 둘(`START_CHARS`)이다.
  - **스킬은 캐릭터당 2개**다. 지금 기본 장착 2개: 세검 = thrust · spin, 대검 = launch · smash.
- 2인 · 태그 솔로 · AI 파트너는 그대로 쓴다(Esc 메뉴).
- 보스를 잡으면 결과 화면이 뜨고, 아무 키로 다시 시작한다. 유물 선택 화면은 이번엔 거치지 않는다.
- 게임 판정 · 수치는 그대로다. 이 흐름(`SLICE`)은 브라우저 시작 흐름만 바꾸고, Node의 봇 테스트 · 재생에는 영향이 없다.
- **이번에 만드는 것:** 캐릭터 2 + 보스 1 + 그 아레나 + UI 화면 5개(타이틀 · 전투 HUD · QTE · Esc 메뉴 · 결과)
- **나중에 확장할 것:** 나머지 캐릭터 3명 · 보스 3체 · 선택 화면 · 유물 카드. 테마 사양 표에 있는 그 줄들은 확장 때 참고용이다.

# 이 세션의 질문
**"어둡고 차가운 실사 조명 속에서, 얼굴을 가린 실루엣과 빛만으로 AAA 다크 히어로 분위기가 나는가."**
- **레퍼런스:** `tools/style/ref4/s3_dark_real` — 실사 3D 포스터 · 조각상 렌더, 실사풍 일러스트 4장
- **목표 수준:**
  - 표 1 Inside의 공식(단순한 인물 + 조명 · 안개 · 실루엣)을 뼈대로 하고, 레퍼런스의 재질감(가죽 · 마모 금속 · 사슬)과 발광 강조를 얹는다.
  - **실사 디테일 경쟁은 하지 않는다.**
  - 지금 모델로 실사 얼굴 · 몸을 만들면 마네킹처럼 보이므로, 얼굴을 가리는 디자인과 빛으로 푼다.
- **예상 작업량:** 세션이 혼자 도는 시간 기준 8~12시간(새 렌더 경로 + 볼륨 빛 + 하드서피스 모델 + 무거운 캡처) (빠른 테스트판). 라운드마다 걸린 시간을 PROGRESS에 적고, 12시간을 넘길 것 같으면 그 시점에 디렉터에게 알린다(멈추지 않음).

# 절대 규칙
- 3단계 최종을 `index_v5.html`로 보존한다(`index_v1~v4.html`은 그대로). 게임은 `index.html` 한 파일, 테스트는 `tools/`.
- **자주 바뀌는 것은 전부 파일 위쪽 데이터 구역에 데이터 표로 둔다.** 한글 주석을 단다. 코드에 숫자를 직접 박지 않는다.
  - 이 테마의 표: `T3`(렌더 · 색 · 모델 · 애니메이션 · 아레나 · 이펙트 · UI · 카메라 · 자동 품질)
  - 공통 표: `ART`(지금 테마 · 등록된 테마 · 바꾸는 키), `FONTS`(넣은 글꼴 · 라이선스 · 글자 범위 · 크기)
- `window.PIPE`는 키를 추가만 한다. 새 함수는 PIPE에 넣고, 점검에서 함수가 있는지부터 확인한다(3단계에 빠뜨린 적 있음). 행 번호 대신 코드 문자열로 위치를 찾는다.
- **게임 판정에는 시드 난수만 쓴다.** 테마는 화면만 바꾼다.
  - 카메라 · 입자 · 2차 움직임 · 애니메이션 계단 · 획 끓임 같은 연출 값은 판정에 쓰지 않는다.
  - 같은 시드 · 같은 입력이면 테마 0과 테마 3의 결과가 3단계와 바이트 단위로 같아야 한다.
- 확인하지 않은 것을 확인한 것처럼 쓰지 않는다. 헤드리스(SwiftShader) 프레임 시간은 실제 GPU 프레임이 아니라고 표기한다.
- 스펙에 없는 규칙을 만들면 체크리스트에 ★로 따로 적는다.
- **레퍼런스 속 캐릭터 · 로고 · 화면 구성을 그리지 않는다.**
  - 해당: 나이트런 유닛과 로고, 레피아, 에어리스, 배트맨 아캄 나이트, X-23, 배트맨 후 래프스, 화이트 다이아몬드, 데스도어의 까마귀 주인공 · 등장인물 · 로고 · UI 아이콘, 레퍼런스 일러스트의 개별 캐릭터 디자인 등
  - 우리 캐릭터 · 보스를 이 테마의 규칙으로 다시 디자인한다. **이번 테스트판은 세검(청) · 대검(적) + 애저 워든**만 만든다.
- 모호한 부분은 기본값을 정해 체크리스트에 적고 진행한다. **멈추는 곳은 두 군데뿐이다:**
  1. 되돌릴 수 없는 결정
  2. 외부 에셋(모델 · 텍스처 · 소리) 출처 · 라이선스 판단이 필요할 때. OFL 글꼴(npm `@fontsource/*` 등)은 허용한다.
  - 디렉터가 "멈추지 말고 끝까지"라고 하면 ②는 에셋 없이 진행하고 그렇게 했다고 적는다.

# 실수·누락 방지 (3단계까지 배운 것)
1. 첫 단계에서 `tools/PROGRESS_4_T3.md`를 만든다. 스펙 한 줄마다 ID, 구현 위치, 확인 방법을 적고 라운드마다 갱신한다.
2. 단계마다 그 단계의 규칙 점검 항목을 먼저 쓰고(check15 뒤에 `4T3` 블록), 구현한 뒤 통과를 확인한다.
3. **보고하는 숫자는 최종 빌드로 다시 돌린 것만 쓴다.** 빌드 해시를 기록하고, 서빙 사본이 최종 빌드와 같은지(three 경로만 다른지) 비교한다.
4. 테스트 스크립트가 게임 상태를 바꾸면 다음 장면 전에 되돌린다.
5. **앵커링:** 3단계까지 "그래픽 바꿔 줘"에 지금 그림을 조금만 고치는 쪽으로 끌려간 일이 반복됐다. 아래 '앵커링 금지' 절을 절대 규칙으로 지킨다.
6. 렌더 점검에서 앞 장면의 화면 효과(흑백 카드 · 글리치)가 다음 장면에 새어 나온 적이 있다. 장면마다 효과 타이머를 먼저 0으로 만든다.
7. 자동 품질이 큰 프레임을 건너뛰어 동작하지 않은 적이 있다(3단계에서 고침). 가짜 느린 프레임으로 단계 내리기가 실제로 일어나는지 확인한다.
8. 채움 모드에서 초상을 저해상도 좌표로 그린 적이 있다. 이 테마의 HUD는 기기 픽셀 좌표로 그린다.
9. 테마를 바꾼 뒤 이전 테마의 재질 · 소품 · 렌더 타깃 · 텍스처가 남지 않게 정리(dispose)한다. 드로우콜 · 텍스처 수로 확인한다.
10. 2단계에서 렌더 도구가 카메라 높이를 못 찾아 NaN이 난 적이 있다. 크롭 좌표가 숫자인지 먼저 확인한다.

# 앵커링 금지 (절대 규칙 — 3단계 그림에 끌려가지 않기)
디렉터 결정: **아트풍뿐 아니라 모델링 · 모션 · UI도 전부 이 테마에 맞춰 새로 만든다.** 3단계 화면 · 모델 · 동작 · UI를 고쳐서 만드는 것이 아니다.

1. **순서:** 레퍼런스 → 특징 표 → 디자인 시트(캐릭터 · 보스는 E, UI는 U) → 스펙 표 → 랩. 그다음에야 3단계 렌더 · 모델 · 동작 · UI 코드를 연다.
   - 해당 코드: `data30.js`의 `STYLE` 값, `style30.js` 셰이더, 캐릭터 · 보스 메쉬를 만드는 함수, 자세 값, HUD · 메뉴 그리기 코드
   - **예외 (작업 순서 1의 공통 기반):** 훅을 끼울 자리만 찾으려고 열어 볼 수 있다. 렌더 루프(`style30.js`의 `renderer.render` 부근과 splice30의 `if (STYLE.on) return renderStyle` 자리), HUD 그리기 진입점(`hud30.js`), 메뉴 줄 목록(`menu30.js`). 셰이더 내용 · STYLE 값 · 메쉬 빌더 내용은 읽지 않는다.
2. **랩(`lab4_t3.html`)은 3단계 코드를 가져오지 않고 새로 짠다.**

| 구분 | 내용 |
| --- | --- |
| 가져와도 되는 것 (판정 · 동작 호환용 데이터만) | 판정용 숨은 리그 전체(아래 3번), 동작 이름 · 길이(초) · 판정 시점 · 이동 값, **`MOTION`의 게임 값**(`leapH` · `airT` · `hang` · `dashDist` · `slide` · `knock` — 몸을 실제로 움직이는 값이라 바꾸지 않음), 판정 크기(히트 반경 · 키), 게임 상태 값, 메뉴 · 입력 흐름(무엇을 누르면 어디로 가는지) |
| 가져오면 안 되는 것 (보이는 것) | 보이는 모델에 3단계 메쉬 · 부품 모양 · 비율, **보이는 자세 값(관절 각도)**, **`MOTION`의 화면 값**(`runLean` · `runBob` · `smearW` · `dashGhosts` · `landFx` · `airZoomMin`), 재질 · 셰이더 · 후처리 코드와 값, 팔레트, 아레나 소품, **HUD · 메뉴 · 선택 화면 · 타이틀의 모양 · 배치 · 글꼴 · 화면 전환** |

3. **판정용 숨은 리그 (필수 — 게임 판정 불변의 핵심)**
   - 게임 판정은 매 프레임 3단계 리그에서 위치를 읽는다. 예: 보스 내려찍기 · 사격 지점(`measureJoint` → `SLAM_AT` · `SHOT_AT`), 손 뼈의 잡기 낙하 지점, 도깨비 `dkTip`, 위핑 벨 약점 오브젝트.
   - 그래서 **모든 테마에서 3단계 리그(뼈 · 동작 클립 · 약점 오브젝트 · 이름 붙은 노드)를 그대로 만들고 그대로 돌린다.** 이것이 '판정용 숨은 리그'다.
   - 화면에서만 숨긴다: 카메라가 그리지 않는 레이어로 옮긴다. `.visible`은 바꾸지 않는다(판정 코드가 읽을 수 있음).
   - 새 모델은 **보이는 리그**다. 숨은 리그의 위치 · 방향 · 상태 · 클립 시간을 따라가고, 새 자세 · 새 뼈 길이 · 애니메이션 계단 · 2차 움직임은 보이는 리그에만 적용한다.
   - 타격 프레임에서 보이는 무기 끝과 판정 지점의 거리가 판정 반경의 25% 이하가 되게 맞춘다(보이는 것과 맞는 곳이 같게). 점검 항목으로 잰다.
   - Node(봇 테스트 · check15)에서는 숨은 리그만 있으면 되므로 판정 결과가 3단계와 같다.
   - **`STYLE.on`은 모든 테마에서 true로 둔다.** QTE · 도약 곡선 · Esc 멈춤 · 타이틀이 이 값에 묶여 있다. 테마는 `artFrame` 등 훅으로만 화면을 넘겨받는다.
   - 게임에 옮길 때 3단계 코드에서 화면용으로 다시 쓸 수 있는 것은 **배관**뿐이다: 렌더 타깃 관리, 자동 품질, 채움 모드, 입력 · 메뉴 흐름. 화면에 보이는 것은 전부 테마 3 전용 코드(`parts/t3_*.js`)로 그린다.
4. **3단계와의 거리 게이트** — 잴 수 있게 된 라운드부터 잰다(X1 · X4는 라운드 3 랩, X2 · X3는 라운드 5, X5는 라운드 7, X6은 라운드 8). **최종 전달 전에 전부 통과**해야 한다. 중간 디렉터 시트(D)는 통과와 관계없이 보내고 결과를 같이 적는다.

# 극한으로 끌어내는 방법 (이번 세션의 핵심)

## A. 레퍼런스를 특징 목록으로 쪼갠다
- 레퍼런스 이미지와 REFS_4.md를 보고 **구체 특징 15개 이상**을 표로 만든다(빠른 테스트판).
  - 열: ID · 특징 · 근거 이미지 · 게임에서 쓰는 곳(캐릭터 / 보스 / 아레나 / 이펙트 / UI / 초상) · 구현 방법 · 상태(✗ / △ / ✓)
  - 특징은 구체적으로 쓴다. 예: "머리카락 = 안쪽 디테일 없는 검정 한 덩어리 + 흰 하이라이트 줄 2~3개"
- 카메라 거리 때문에 게임 화면에서 안 보이는 특징(얼굴 세부 등)은 '초상 · UI용'으로 표시하고 거기서 구현한다.
- 목표: 최종 ✓ **80% 이상**

## B. 화면 반복 루프 (라운드)
- **한 라운드**
  1. 바꿀 것 3개 이하를 고른다. 특징 표의 ✗ · △ 중 화면 비중이 큰 것부터.
  2. 빌드한다.
  3. 고정 장면 6장을 캡처한다: 보스 전투 2장(페이즈 1 · 페이즈 2, 다른 순간) · 마무리 순간 · 대시 잔상 · QTE 진행 · 타이틀 또는 HUD. 라운드 6부터는 **동작 프레임 띠**(1순위 동작 4개 × 8프레임), 라운드 8에는 **UI 화면 시트**도 만든다
  4. [레퍼런스 | 이전 라운드 | 이번 라운드] 시트를 만든다.
  5. **이미지를 직접 보고** 평가하고, G1 · G2 수치를 잰다.
  6. PROGRESS에 시트 경로 · 바꾼 것 · 수치 · 남은 차이를 적는다.
- **최소 8라운드**를 돈다(빠른 테스트판). 라운드 1~3은 랩(렌더 규칙 · 색 · 카메라 · 빛 + 새 모델 첫 판), 4~5는 게임 이식(모델 완성 · 아레나 · 이펙트), 6~7은 모션, 8은 UI가 중심이다.
- 숫자만 바꾼 라운드는 3번 연속 금지다.
- 라운드 평가(이미지 직접 평가 + G1 · G2)가 2라운드 연속 나아지지 않으면 **구조**를 바꾼다(모델 · 조명 · 구도 · 렌더 규칙 · 카메라 중 하나).
- 첫 라운드는 레퍼런스보다 세게 하고 줄여 간다.

## C. 블라인드 패널
- **언제 · 누구에게** (빠른 테스트판)
  - 라운드 4: 이 작업을 안 본 하위 에이전트 1명, 그래픽 점수만(빠른 방향 확인)
  - 최종: 하위 에이전트 **3명**(매번 새로), 그래픽 · 모션 · UI 세 점수 + A/B + X1 · X6
- **무엇을:** 이름 없이 [레퍼런스 묶음 시트 + 새 화면 3장]을 주고 묻는다.
  - "새 화면이 레퍼런스와 같은 아트 디렉션으로 보이는 정도 1~10점"
  - "가장 큰 차이 3개"
  - "필터를 씌운 것 같은 인상이 있나"
  - 최종에 추가: [동작 프레임 띠] "움직임이 이 그래픽과 어울리고 다이나믹한가 1~10점" · [UI 화면 시트] "UI가 게임 화면과 같은 아트 디렉션인가 1~10점"
- **별도 A/B:** [3단계 화면, 새 화면] 중 레퍼런스에 가까운 쪽을 고르게 한다. 새 화면이어야 한다.
- **목표:** 그래픽 · 모션 · UI 세 점수 모두 3명 평균 **7점 이상**(3단계 그래픽은 자기 레퍼런스 대비 5~6점), '필터 같다' 0명
- **질문은 고정한다.** 의도 · 프롬프트는 알려 주지 않는다. 점수를 올리려고 질문을 바꾸지 않는다.

## D. 디렉터 체크포인트 (멈추지 않음)
- 라운드 3(비교 시트 + 디자인 시트 + UI 목업)과 라운드 6(비교 시트 + 동작 프레임 띠)이 끝나면 디렉터에게 보내고 계속 진행한다. 답이 오면 다음 라운드에 반영한다.
- 디렉터가 "더 바꿔"라고 하면 수치 몇 개를 조정하지 않는다. 특징 표에서 레퍼런스와 다른 줄을 먼저 보이고, 줄 단위로 크게 바꾼다.

## E. 모델링을 이 테마에 맞춰 새로 만든다 (디렉터 결정)
- **범위:** 세검 · 대검 + 애저 워든 + 워든 아레나 소품을 이 테마용으로 **처음부터** 다시 만든다. 3단계 메쉬 코드를 고치지 않고, 테마 전용 모델 빌더 `parts/t3_model.js`를 새로 쓴다. 나머지 캐릭터 · 보스도 나중에 같은 빌더로 늘릴 수 있게 짠다.
- **디자인 시트 먼저:** 3D를 만들기 전에 세검 · 대검 · 워든의 실루엣 시트를 SVG로 그린다.
  - 각도: 정면 · 측면 · 게임 카메라 각도
  - 테마 모델링 규칙을 따르고, 무기 · 색 배치를 표시한다.
  - 처음 보는 에이전트 1명에게 "레퍼런스와 같은 디자인 언어(형태 · 비율 · 덩어리)의 캐릭터로 보이나 1~10점"을 묻고 7점 이상이면 3D로 간다.
  - **최대 3번** 다시 그리고, 그래도 7점이 안 되면 가장 높은 판으로 진행하고 PROGRESS에 적는다(무한 반복 금지).
  - 라운드 3 디렉터 메시지에 같이 보낸다.
- **유지하는 것** (판정 · 동작 호환)
  - 판정용 숨은 리그(앵커링 금지 3번)는 3단계 그대로. 보이는 리그는 그 뿌리(위치 · 방향)를 따라간다.
  - 판정 크기(지금 데이터 그대로)
  - **화면 실루엣의 폭 · 키는 판정 크기의 ±15% 안**에 둔다. 보이는 몸과 맞는 범위가 어긋나지 않게 하기 위해서다.
- **바꿔도 되는 것 (보이는 리그만):** 뼈 이름 · 길이 · 비율 · 굵기.
  - 새 자세(F)를 만들기 전까지는 3단계 클립을 임시로 돌려 확인만 한다(관절 각도 위주라 대부분 돈다). 최종에는 1 · 2순위 동작이 전부 새 자세여야 한다.
  - 다리 길이가 바뀌면 몸 높이 위치 값은 비율로 보정한다. 깨지는 자세는 테마 데이터로 보정한다.
  - 추가 뼈(머리카락 · 망토 · 끈 체인)는 화면 전용이다.
- **테마 모델링 규칙:** 아래 테마 사양의 '모델링 규칙' 표를 따른다. 스타일에 맞춰 비율 · 면 구성 · 디테일 크기를 정하는 표다.
- **코드로 만들 수 있는 것**
  - 회전체(Lathe), 압출(Extrude, 모서리 깎기)
  - 튜브(곡선을 따라 — 머리카락 다발 · 끈 · 사슬)
  - 판 묶음(머리카락 카드 · 망토 · 치마 자락)
  - 정점 조작(부풀리기 · 비틀기 · 법선 옮겨 쓰기), 메쉬 합치기
- **드로우콜은 줄인다:** 같은 뼈에 붙는 부품은 한 메쉬로 합치고, 같은 재질은 묶는다. 삼각형 수는 수단이지 목표가 아니다. 실루엣이 레퍼런스처럼 읽히는지가 목표다.
- **2차 움직임(화면만):** 머리카락 · 망토 · 끈 · 사슬을 스프링 · 체인으로 흔든다. 시간 기반이고 판정과 무관하다.
- **얼굴:** 게임 카메라 거리에서 보이는 수준까지만 만든다. 얼굴 그림은 초상(UI)에서 한다.

## F. 모션을 새 모델 · 테마에 맞춰 다시 만든다 (디렉터 결정 — 더 다이나믹하게)
- **범위:** 세검 · 대검과 워든의 동작 자세를 이 테마의 새 모델 비율과 모션 언어(테마 사양 표)로 **새로** 만든다. 3단계 자세에 배율을 곱하는 방식이 아니다.
- **자세는 데이터다:** 새 자세 값은 데이터 표 `T3.poses`에 둔다. 동작 이름 · 키 시점 구조는 3단계 클립과 같게 해서 게임 코드가 그대로 부르게 한다.
- **그대로 두는 것 (판정 · 게임 시간에 닿음)**
  - 동작 이름 · 길이(초) · 판정 시점 · 이동 값(대시 거리 · 앞으로 미끄러짐 · 넉백)
  - 적중 정지 · 전체 정지 시간: 3단계 값 그대로 둔다. 바꾸면 재생 해시(T3)와 3단계 전체 정지 기준(4% 이하)이 깨진다.
  - 판정이 읽는 뼈 위치는 판정용 숨은 리그가 계속 계산한다(앵커링 금지 3번). 새 자세는 보이는 리그에만 적용하고, 타격 프레임의 보이는 무기 끝을 판정 지점에 맞춘다(거리 ≤ 판정 반경 25%).
- **우선순위**

| 순위 | 동작 | 규칙 |
| --- | --- | --- |
| 1순위 (화면에 가장 오래 보임) | 대기, 달리기, 대시, 평타 전 타수(세검 · 대검), 패리, 피격 · 넘어짐, QTE 자세, 워든 기본 공격 · 예고 · 큰 패턴 | 전부 새로 |
| 2순위 | 스킬 2개 × 2명(세검 thrust · spin, 대검 launch · smash), 착지, 부활 | 전부 새로. 마무리는 스킬 동작을 다시 쓰므로(디렉터 결정) 자동으로 따라옴 |
| 3순위 | 결과 화면 자세 등 나머지 | 시간이 모자라면 임시로 3단계 자세. 최종 보고에 목록을 적음 |

- **다이나믹하게 만드는 방법** (화면만, 테마 사양의 '모션 언어'가 어떤 것을 얼마나 쓸지 정함)
  - 몸 전체가 한 곡선을 그리는 액션 라인
  - 큰 예비 동작
  - 타격 뒤 따라 넘어가는 오버슈트, 핵심 자세 유지
  - 애니메이션 계단, 스미어, 임팩트 프레임
  - 머리카락 · 망토 · 사슬의 2차 움직임
  - 카메라 언어(확대 · 흔들림 · 따라가기)
- **측정**
  - **M2:** 1순위 공격 동작마다 예비 구간에서 무기 끝이 타격 반대 방향으로 몸 키의 0.25 이상 이동하고, 타격 뒤 오버슈트가 있어야 한다.
  - **X5:** 3단계 자세와의 실루엣 차이(앵커링 금지 4번)
  - **패널 모션 점수:** 7점 이상
- **동작 프레임 띠:** 1순위 동작 4개를 8프레임씩 같은 카메라로 찍어 한 장에 놓는다. 라운드 6부터 매 라운드 시트에 넣는다.

## U. UI를 새 테마에 맞춰 전부 다시 만든다 (디렉터 결정 — 더 다이나믹하게)
- **범위 (빠른 테스트판 5개):** 타이틀, 전투 HUD(체력 · 파형 동그라미 3개 · 랠리 · 기술명 · QTE 칸 · 1P 키 표시 · 보스 이름과 체력), QTE, Esc 메뉴(모든 탭), 결과 화면 + 화면 전환. 선택 화면 · 유물 카드는 이번엔 없다.
- **UI 목업 시트 먼저 (D2)**
  - 구현 전에 위 화면 5개를 테마 스타일 목업(HTML/SVG)으로 만든다.
  - 처음 보는 에이전트 1명에게 "레퍼런스 묶음과 같은 디자인 언어(형태 · 색 · 글꼴 느낌)의 UI인가 1~10점"을 묻고, 7점 이상이면 구현한다.
  - **최대 3번** 다시 만들고, 그래도 안 되면 가장 높은 판으로 진행하고 PROGRESS에 적는다.
  - 라운드 3 디렉터 메시지에 같이 보낸다.
- **3단계 디렉터 결정은 유지한다** (UI가 바뀌어도 규칙은 그대로)
  - 스킬 연출은 기술명만(큰 컷인은 옵션, 기본 끔)
  - 화면 글자 동시 3개 이하(U1)
  - 싸우는 화면에는 1P 키만(U2)
  - Esc = 메뉴 + 게임 멈춤
  - 타이틀 → 아무 키
  - QTE 칸 색 · 키 판독
- **배치는 바꿔도 된다.** 단, 바꾸면 U1 · U2 · QTE 판독을 다시 확인하고, 기술명은 늘 같은 자리에 둔다(눈이 한 곳만 보면 되게).
- **다이나믹하게 만드는 방법** (테마 사양의 'UI 움직임' 표가 모양을 정함)
  - UI 요소 등장 · 퇴장 움직임
  - 피격 · 랠리 · 파형 저장 · 패리 성공에 반응하는 HUD 움직임
  - 기술명 등장 연출
  - 화면 전환 와이프
  - **흐름을 끊지 않는다:** UI 움직임은 게임을 멈추거나 입력을 막지 않는다. 기술명 연출은 0.8초 표시 시간 안에서만 한다.
- **글꼴:** `FONTS` 표. OFL 글꼴을 `pyftsubset`으로 잘라 base64로 넣거나, 세션이 직접 그린 원본 비트맵 글꼴을 쓴다. 3단계 F7 글꼴 데이터는 쓰지 않는다.
- **배관:** 3단계 HUD 캐시 · 기기 픽셀 그리기는 재사용해도 된다(모양이 아니라 그리는 방법이라서).

## G. 아레나 (빠른 테스트판: 워든 아레나 하나)
- 워든 아레나 하나를 가장 완성도 높게 만든다. 바닥 톤 · 강조색 · 소품 실루엣 · 빛 방향을 테마 사양 표의 워든 줄대로.

## 이펙트
- 짧은 선 불꽃 + 점광 깜빡임
- 피(어두운 데칼), 연기, 물 튀김
- 자파: 보라 발광 + 연기

## UI (U) · 초상 (H)
- **글꼴:** Barlow Condensed + IBM Plex Sans KR(OFL)
- **패널:** 반투명 어두운 패널, 얇은 선, 최소 장식. 체력 = 얇은 막대
- **초상:** 게임 3D 모델을 극적 조명으로 렌더한 스튜디오 샷(헬멧 실루엣 + 역광)을 시작할 때 렌더 타깃에 구워서 쓴다.

## UI 움직임 (U)
- 얇은 선이 그어지며 패널이 열린다(전술 HUD 느낌, 글리치 아님).
- 정보가 갱신될 때 짧은 스캔 라인이 지나간다.
- 피격 시 화면 가장자리에 붉은 비네트가 짧게 뜬다.
- 화면 전환은 암전 후 빛줄기다.
